## 2. Архитектурные правила

1. Сервер является источником истины.
2. Клиент не присылает готовый результат исследования, скана, крафта,
   зарядки или расхода ресурсов.
3. Любой state transition повторно проверяется сервером.
4. Аспекты, исследования, вис, узлы, essentia, инфузия и варп реализуются
   внутри проекта.
5. Не использовать Patchouli вместо Thaumonomicon.
6. Не использовать Create/AE2/Botania вместо core-механик.
7. Curios разрешён позднее только для бывших Baubles slots.
8. Данные отделяются от runtime:
   - аспекты;
   - исследования;
   - страницы;
   - scans;
   - arcane recipes;
   - wand rod/cap definitions;
   - node types/modifiers.
9. Не создавать параллельные реестры с дублирующим состоянием.
10. Все операции расхода должны быть атомарными.
11. Не доверять NBT предмета без проверки registry и player state.
12. Не переносить декомпилированный Java-код механически.

## 4. Следующая вертикаль

После зелёного стабилизационного барьера реализуй:

**«Первая тауматургия: жезл → видимый магический мир → узел в банке →
вис → Arcane Workbench»**

Не начинай алхимию, инфузию или advanced wand content.

### 4.1 Базовые компоненты жезла

Добавь:

- iron wand cap;
- wooden wand rod;
- basic iron-capped wooden wand.

Требования:

- определения rod/cap data-driven;
- стабильные ID;
- отдельные capacity/cost properties;
- wand stack хранит состав и текущий вис;
- шесть независимых значений:
  - Aer;
  - Terra;
  - Ignis;
  - Aqua;
  - Ordo;
  - Perditio;
- tooltip показывает capacity и текущий запас;
- сервер владеет изменением запасов;
- копирование, crafting, save/load и sync не теряют NBT.

Используй классические рецепты:

- `WandCapIron`;
- `WandBasic`.

### 4.2 Превращение книжной полки

Любой корректно собранный базовый жезл превращает bookshelf в Thaumonomicon.

Критически важно:

- заряд жезла не требуется;
- вис не расходуется;
- нулевой запас вис не блокирует действие;
- сервер проверяет held wand и target block;
- успешное действие проигрывает классический sound/FX;
- невалидная цель ничего не меняет и не расходует.

Не переносить это правило автоматически на другие wand interactions. Поведение
превращения crafting table сначала подтвердить по оригинальному bytecode.

### 4.3 Обычный аурный узел

Добавь минимальный настоящий aura node:

- текущий и максимальный запас шести примальных аспектов;
- обычный `NodeType`;
- обычный `NodeModifier`;
- сохранение в мире;
- sync клиенту;
- безопасное восстановление;
- классический renderer из `nodes.png`;
- классические particles/FX;
- scan target типа node/phenomenon;
- отображение параметров через Thaumometer;
- серверную зарядку жезла.

Правило видимости:

- без активного Таумометра и без надетых Очков откровения узел практически
  невидим: нельзя оставлять яркую полностью читаемую сферу;
- активный Таумометр раскрывает узел только в предусмотренном режиме
  наблюдения/сканирования;
- надетые в vanilla head slot Очки откровения постоянно раскрывают узел;
- решение о раскрытии принимается из фактического состояния игрока, а не из
  доверенного клиентского флага;
- невидимость не должна удалять серверную hit/scan сущность или ломать sync;
- точные alpha, render passes, depth/blend и частицы сначала подтвердить по
  оригинальному renderer TC4.

Для этой вертикали не добавлять:

- Hungry;
- Sinister;
- Tainted;
- Unstable;
- Pure;
- advanced node equipment.

Узел должен быть достижим в обычной игре. Debug-команда допустима для тестов,
но не заменяет gameplay acquisition.

### 4.4 Очки откровения

- обычный слот шлема, без обязательного Curios;

- серверно проверяемый эффект раскрытия узлов;
- сохранение обычных armor semantics и отсутствие дублирующих capability.

Текущее `legacy/goggles.json` уже доказывает:

- категория `ARTIFICE`;
- родитель `THAUMOMETER`;
- concealed progression;
- аспекты исследования `Sensus 3 + Auram 3 + Praecantatio 3`;
- recipe page `Goggles`.

Не придумывай новый рецепт или новый research parent. Сначала восстанови

### 4.5 Зарядка жезла

Серверный алгоритм:

1. Проверить жезл.
2. Проверить узел и дистанцию.
3. Определить отсутствующий в жезле вис.
4. Не превышать wand capacity.
5. Не списывать из узла больше доступного.
6. Изменить node и wand atomically.
7. Синхронизировать оба состояния.
8. Отправить клиенту только FX/result.

Добавь защиту от:

- повторных пакетов;
- зарядки из удалённого чанка;
- смены предмета во время операции;
- уничтоженного узла;
- переполнения;
- отрицательных значений.

### 4.6 Узел в банке

Реализуй классическую механику `NODEJAR`:

1. По оригиналу подтвердить структуру банки, допустимые блоки и точное
   wand-взаимодействие.
2. Сервер проверяет завершённое исследование, структуру, held wand, дистанцию,
   узел и состояние чанка.
3. После успешного действия мир и узел изменяются одной логической
   транзакцией.
4. В предмет/блок банки переносятся как минимум:
   - node type;
   - node modifier;
   - текущий vis;
   - максимальный vis;
   - все необходимые стабильные идентификаторы/данные визуализации.
5. При размещении данные восстанавливаются один раз; нельзя дублировать узел
   повторным пакетом, ломанием, поршнем, выгрузкой чанка или save/reload.
6. Звук, частицы, модель и текстуры соответствуют TC4.

Добавь готовый `jarred aura node` в creative inventory. Это инструмент
тестирования, а не замена survival progression:

- stack создаётся с валидным детерминированным обычным узлом;
- содержит безопасные примальные значения, описанные в одном factory;
- tooltip явно показывает, что это готовый узел;
- creative stack и survival-полученный stack используют один schema/versioned
  codec и один путь размещения;
- не заставляй пользователя искать worldgen-узел для ручной проверки.

Исследование `NODEJAR` в текущем импорте concealed, имеет родителя
`NODEPRESERVE`, аспекты `Auram 6 + Lucrum 3 + Permutatio 3 + Motus 3` и
страницу рецепта `NodeJar`. Не снимай `inactive`, пока родительская цепочка,
механика, рецепт и страницы не стали реально достижимы.

## 7. Отдельный обязательный UI-протокол

UI — зона повышенного риска. Не работай с ним как с обычным кодом.

### 7.1 Перед изменением

1. Назови конкретный экран и элемент.
2. Укажи source texture и её физический размер.
3. Найди соответствующий GUI/renderer-класс TC4.
4. Зафиксируй:
   - texture atlas size;
   - source X/Y/W/H;
   - destination X/Y/W/H;
   - GUI Scale;
   - screen resolution;
   - anchor;
   - render order;
   - blend/tint state.
5. Покажи пользователю, какие значения будут изменены.
6. Не трогай подтверждённые элементы соседнего интерфейса.

### 7.2 Запреты

Запрещено:

- подбирать crop и координаты на глаз;
- добавлять самодельные рамки или декор без референса;
- менять несколько независимых UI-зон одним экспериментом;
- менять механику вместе с геометрией без необходимости;
- утверждать визуальную корректность после compile/test;
- использовать скриншот с неизвестным GUI Scale как точную метрику;
- возвращать старые трансформации из истории чата без проверки актуального
  baseline;
- скрывать вкладки или узлы ради исправления геометрии;
- изменять first-person и third-person transform одновременно.

### 7.3 Настраиваемые параметры

Все координаты и размеры вынести в один подписанный блок:

- `OFFSET_X`;
- `OFFSET_Y`;
- `WIDTH`;
- `HEIGHT`;
- source crop;
- scale;
- hand translation/rotation;
- third-person translation/rotation/scale.

Для каждого параметра оставить короткое русское объяснение:

- плюс X — вправо;
- плюс Y — вниз;
- что именно меняет параметр;
- зависит ли он от GUI Scale;
- влияет ли на frame, glass, content или hands.

Пользователь определяет финальную композицию. Агент реализует код и объясняет
значения.

### 7.4 Thaumometer

Разделяй четыре независимых слоя:

1. world view;
2. blue scan glass;
3. golden frame;
4. player hands.

Проверять отдельно:

- frame не обрезан;
- glass не выходит за золотые границы;
- frame и glass масштабируются согласованно;
- руки видны при взгляде вверх, прямо и вниз;
- руки соответствуют текущему скину;
- frame слегка перекрывает руки только по подтверждённому референсу;
- hotbar остаётся видимым;
- first-person overlay не влияет на third-person model;
- third-person model не отображается ребром.

### 7.5 Thaumonomicon

Проверять отдельно:

- background заполняет внутреннюю область;
- вкладки используют классические sprites;
- inactive category не исчезает, если содержит видимое inactive research;
- node icon центрирован;
- доступный узел мигает самой классической рамкой;
- нет дополнительной квадратной обводки;
- узлы одной категории не пересекаются;
- recipe result и ingredients центрированы;
- atlas crop не захватывает соседние полосы;
- page text и images не выходят за страницу.

### 7.6 Arcane Workbench Screen

Перед реализацией:

- извлечь `gui_arcaneworkbench.png`;
- проверить оригинальный `GuiArcaneWorkbench`;
- составить таблицу всех слотов и regions;
- определить wand slot, result slot и vis indicators;
- только после этого писать Screen.

Не использовать обычный vanilla Crafting Screen как финальный интерфейс.

### 7.7 Визуальная приёмка

После каждой UI-итерации:

1. Собрать JAR.
2. Полностью перезапустить Minecraft.
3. Зафиксировать resolution и GUI Scale.
4. Сделать новый скриншот.
5. Сравнить только заявленный изменённый элемент.
6. Получить подтверждение пользователя.
7. Записать принятые значения как baseline.

Без нового скриншота статус:

`COMPILED_NOT_VISUALLY_VERIFIED`

Нельзя писать «исправлено визуально».

## 8. Работа с версиями и JAR

Текущее правило проекта:

- при изменении повышать `mod_version`;
- собирать versioned JAR;
- проверять внутреннюю версию;
- вычислять SHA-256;
- устанавливать новый JAR в Minecraft только после успешных тестов;
- предыдущий JAR перемещать в Корзину, не удалять безвозвратно;
- убедиться, что в `mods` осталась одна версия.

Любые операции вне workspace, включая установку JAR и перемещение в Корзину,
выполнять только в пределах прямого запроса пользователя и доступных разрешений.

## 9. Проверки

Минимум после каждого логического изменения:

- targeted unit tests;
- полный `./gradlew test`;
- `./gradlew build`.

После datapack, registry, BlockEntity, Menu или network изменений:

- `./gradlew runGameTestServer`.

Добавить тесты для:

- wand NBT round-trip;
- capacity boundaries;
- vis add/consume transaction;
- node persistence;
- node-to-wand transfer;
- node visibility without revealing equipment;
- node visibility with active Thaumometer;
- node visibility with Goggles in head slot;
- jar structure validation;
- jar node NBT/codec round-trip;
- jar capture/place atomicity and duplicate-packet rejection;
- creative jar factory validity;
- invalid/remote node;
- arcane recipe parsing;
- insufficient vis;
- research gate;
- atomic crafting;
- bookshelf conversion with zero vis;
- Discovery security checks.
- research activation/page linkage for `GOGGLES` and `NODEJAR`;
- hidden → visible → available → completed research transitions.

Отдельно провести:

- client Play Mode;
- world save/reload;
- ordinary dedicated server;
- two-client multiplayer.

Всегда разделять доказательства:

- compilation;
- unit test;
- GameTest;
- resource reload;
- client visual;
- dedicated server;
- multiplayer.

## 10. Definition of Done

Вертикаль завершена только когда одновременно:

- работает survival loop жезл → раскрытие/скан узла → зарядка → банка →
  arcane crafting;
- готовый узел в банке доступен в creative для тестирования;
- Очки раскрывают узлы только при фактическом ношении;
- книжная полка превращается в Thaumonomicon даже жезлом с нулевым vis;
- все связанные исследования актуализированы и достижимы;
- unavailable pages заменены рабочими страницами;
- оригинальные текстуры/модели имеют provenance;
- unit, build, GameTest и resource validation зелёные;
- проведены отдельные ручные проверки клиента, сохранения мира, dedicated и
  multiplayer;
- UI и рендер не называются исправленными без свежих скриншотов.

## 11. Отчёт после работы

Финальный отчёт должен содержать:

1. Реализованный игровой цикл.
2. Изменённые файлы.
3. Активированные исследования.
4. Точные расхождения с TC4.
5. Результаты каждой категории проверок.
6. Что требует ручного скриншота.
7. Путь и SHA-256 JAR.
8. Инструкцию проверки без команд.
9. Известные риски и следующий безопасный шаг.

Не заявляй, что весь Thaumcraft перенесён. Завершённой считается только
описанная вертикаль.
